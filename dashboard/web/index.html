Cost- and Risk-Aware GitOps Platform

This platform prices and checks a change before it can merge, deploys it only after it passes, then measures it against that prediction while it runs. Everything below is live: the numbers come from the running cluster, and the two buttons run real proofs against it.

Act 1: the problem

A one-line change that nobody could see

A developer changes one line in a deployment file, replicas from 1 to 8, because a load test was slow. Nobody notices. It passes review, because reviewers read code, not capacity. The cluster grows eightfold. The finance team finds out five weeks later, on an invoice, with no way to trace which change caused it.

Every part of that is normal, and every part of it is preventable.

Act 2: govern before it runs

The change is priced at review, not on the invoice

Pull request #1 is real, still open, and still blocked. The gate priced it before anything ran: $11.73 → $370.62, a 3060% increase. It also failed GATE-005, a container with no health check, which Kubernetes could never restart if it hung. So the gate checks safety, not only money.

Cost review normally happens monthly, in a spreadsheet, after the money is spent. Here it happens at code review, before anything is deployed, in the place the decision is actually made.

Pull request #3 shows the same machinery approving a change, worth thirty seconds, otherwise the gate looks like something that only ever says no. The thresholds themselves live in a version-controlled file, and changing them goes through this same gate.

Act 3: Git governs the cluster

Manual changes do not survive here

Every application below came from a merged pull request. Nobody on this project has run a deploy command. There isn't one.

The button edits the live cluster directly, the way an engineer would at 3am during an incident, by setting a memory limit the repository never authorised. Then it waits, and does nothing else.

That is the difference between Git being where the configuration is kept and Git being what the cluster is.

Act 4: measure while it runs

The estimate can be checked, not just trusted

The tiles at the top of this page show reserved spend, what we are paying for, against actual use. The gap between them is waste: money spent on capacity nobody used. Low utilisation is not automatically bad; it is headroom we chose to buy. The point is that it is now a decision instead of an accident.

The cost quoted on the pull request and the cost on this page are computed from the same rate table by the same code. So the estimate can be checked against reality rather than believed.

Act 5: demand drives cost

Demand arrives, the platform responds, and the response has a price

The button puts 600 jobs on the queue. Nothing is reconfigured, the system reacts on its own. Watch three things in order: the queue fills, replicas climb, and the backlog drains again.

Autoscaling demonstrations usually stop at the middle step, replicas went up, therefore it works. That only proves something happened. The queue draining proves it helped.

If you ask what stops it scaling to a thousand: the gate prices an autoscaler at its ceiling, so authorising a maximum is itself a reviewed, costed decision.

Act 6: none of this is a slide

Every claim is a command that fails loudly

The two proofs on this page are the same checks make verify runs in a terminal, driven through fixed API calls instead of a shell. They assert rather than narrate: if the platform stopped reverting drift, or replicas rose without the backlog clearing, the output above would say so in red.

Worth volunteering: the cost figures are modelled, not billed, published cloud rates applied to this cluster. What is demonstrated is that prediction and measurement agree, not that the money is real. The gate can also only price what it renders from Git, so components installed from Helm charts show as $0.00.
